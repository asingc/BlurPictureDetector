TASK (REVISED): Redesign Album/AlbumImage as the sole, strongly-typed access
point for all per-photo and per-person data in BlurPictureDetector
(repo root: c:\Repos\BlurPictureDetector).

This supersedes .20260914-refactory-album-image.md. It keeps that plan's
goal but NARROWS ITS SCOPE to the Album / AlbumImage / PersonRecord typed
access layer, and changes the decisions that, as originally written, would
have caused silent data loss or behaviour regressions. Every change is
justified inline under "WHY THIS DIFFERS" so the original reasoning isn't
lost.

============================================================
GUIDING PRINCIPLE (unchanged)
============================================================
"Clean code with proper level of abstraction without requiring the internal
data structure." No code outside algo/album.py may read/write a raw
results[]/annotation_data dict by key path. All per-image and per-person
state is reached through typed properties/methods.

ADDED COROLLARY (new, and it constrains everything below):
The typed layer is an ACCESS abstraction, not a STORAGE replacement. The
entry dict remains the storage. This is the single most important revision
in this document — see Decision 1.

============================================================
SCOPE — what this task is and is NOT
============================================================
IN SCOPE — algo/album.py and the callers that read/write its data:
  - AlbumImage becomes a fully typed accessor over its entry dict.
  - A new PersonRecord class replaces the four ad-hoc per-body shapes.
  - Album.create() owns the complete AlbumImage set and key assignment.
  - The album.json backup flag.
  - Migrating every consumer off raw dict access onto those types.

EXPLICITLY OUT OF SCOPE — deferred to their own later tasks:
  - THE STATUS STATE MACHINE. `status` is passed through EXACTLY as it
    behaves today: a plain string field, settable by whoever sets it now,
    with today's values and today's transitions. No enum, no
    Unprocessed/Error lifecycle, no legal-transition enforcement. See
    Decision 2 for why this is the right call and what it costs.
  - The "Purge Error" / error-quarantine stage (depends on the status
    machine — see Decision 6).
  - The ProcessStage signature change and the Frame/Body handoff rework.
    Stages keep `process(frames, config) -> frames` for now.
  - Per-stage Album.save() cadence.
  - Deep regrade, including its known
    missing-source-file-deletes-the-entry bug.
  - Resumability after a crash. Restart-from-scratch remains the accepted
    failure mode.

The deferred items are not abandoned — Decisions 2, 6 and the Frame/Body
section below record what was learned so the later task doesn't re-derive
it. The narrowing is deliberate: the typed layer is the prerequisite for
all of them, and it ships and gets verified on its own.

============================================================
THE REVISED DECISIONS
============================================================

--- DECISION 1: AlbumImage is DICT-BACKED, not dict-replacing ---

ORIGINAL PLAN SAID: "AlbumImage's fields are the live in-memory source of
truth; Album.save() must gather every live AlbumImage and serialize it back
into the results[] list."

REVISED: AlbumImage keeps `self._d: dict` (the live entry dict, exactly as
today). Every typed property reads from and writes into `_d`. Album.save()
is UNCHANGED — it still serializes `self._payload` verbatim.

WHY THIS DIFFERS — three concrete failures the original model causes:
  (a) LOSSY ROUND-TRIP. Gathering from typed fields drops every key not
      modeled on the class. Confirmed at-risk keys: `overall_blurry`,
      `processing_shape`, `qualified_for_sharpness` (V5), `_timestamp`
      (V6), `reason`, `persons_detail`, plus anything in the ~1600-photo
      albums already on disk from older schema versions. A single save
      after the refactor destroys them irrecoverably.
  (b) ZOMBIE OBJECTS. Album freshness is stat-based and CROSS-PROCESS (V9).
      Today a stale AlbumImage is harmless — it's a thin view, callers just
      re-fetch. Under the original model, any AlbumImage held across a
      refresh() becomes detached live state whose mutations are either lost
      or resurrected over newer disk data on the next save. That is a data
      corruption vector in a Flask server with background threads.
  (c) DOUBLED SURFACE. It forces a full field inventory to be provably
      exhaustive before the first commit, converting an incremental
      refactor into a big bang.

WHAT IS RETAINED FROM THE ORIGINAL INTENT: callers still never touch a
dict. Every field is a typed property with a docstring. The abstraction
benefit is identical; only the storage decision changes.

Concretely:

    class AlbumImage:
        def __init__(self, album: "Album", entry: dict) -> None:
            self.album = album
            self._d = entry           # live payload dict; storage only

        @property
        def _raw(self) -> dict:
            """Escape hatch for algo/album.py's own merge/import code and
            for the one-release migration window. NOT part of the public
            API — see the module lint guard."""
            return self._d

Reference stability rule (must be documented in the class docstring):
an AlbumImage is valid only until the next `Album.refresh()` observes a
changed stamp. Callers must re-fetch via `album.image(key)` after any
operation that could have let another writer touch the file. This is
already true today; the revision keeps it true instead of making it
subtler.

--- DECISION 2: status is passed through UNCHANGED, and deferred ---

ORIGINAL PLAN SAID: states are Unprocessed/Error/Blur/Clear/Skipped, set
ONCE by the grading stage, derived and not independently settable.

REVISED: do none of it in this task. `AlbumImage.status` is a plain
string property — a typed read/write accessor over `self._d["status"]` and
nothing more:

    @property
    def status(self) -> str:
        """This photo's verdict: "sharp" / "blurry" / "skipped" / "error",
        or "" before grading has run. Deliberately a plain string, not an
        enum or a state machine — the lifecycle is genuinely unsettled
        (see the WHY below) and pinning it down is its own task."""
        return self._d.get("status", "")

    @status.setter
    def status(self, value: str) -> None: ...

Today's writers keep writing it exactly as they do today, just through the
property instead of the dict. No enum, no transition methods, no
validation, no `Unprocessed`, no rename of the wire values.

WHY THIS DIFFERS — the status lifecycle is not actually understood yet:
  - V1: the wire values are "sharp"/"blurry"/"skipped"/"error", not the
    names the original plan proposed. Renaming them breaks every album on
    disk, every string comparison listed in V1, and the webui JS.
  - V3: "set ONCE by the grading stage" is already false — regrade
    re-verdicts graded photos. Any transition table written today would
    have to legalise that, plus whatever else turns up.
  - "skipped" conflates two different facts (no person detected vs. user
    exclusion), and "error" is currently written by a legacy path
    (1_prep_review.py L802/L1132) whose relationship to the live pipeline
    hasn't been traced.
  Encoding a half-understood lifecycle into an enforced state machine is
  worse than leaving it a string: it converts "the semantics are fuzzy"
  into "the app raises in production." The typed-accessor refactor does
  not need the lifecycle resolved, so it shouldn't wait on it.

WHAT THIS TASK STILL BUYS: once every caller reads `image.status` instead
of `entry["status"]`, there is ONE place to grep for writers and ONE place
to later introduce an enum. This refactor is what makes the deferred status
task cheap; doing both at once is what makes it risky.

CARRIED FORWARD for that later task (don't re-derive): the full writer
list is 1_prep_review.py L1354, algo/regrade.py L440, and
algo/results.py::build_result_entries (via the initial entry build). The
full reader list is in V1. `status` absence vs. `""` vs. a real value is
the natural place an "unprocessed" concept would land.

--- DECISION 3: `keep` stays independently settable ---

ORIGINAL PLAN SAID: `keep` is read-only/computed from `stars >= 3`.

REVISED: `keep` is a plain settable property. The stars rule becomes one
named helper that the three callers who want it call explicitly:

    def apply_stars_rule(self, stars: int) -> None:
        """Set stars and derive keep (stars >= 3) — the rule used when a
        verdict change re-rates a photo the user hasn't rated by hand.
        No-op on stars when `stars_manual` is set."""

WHY THIS DIFFERS: per V2, llm_culling.py sets keep from burst rank, not
stars. Deriving `keep` would silently change LLM culling output for every
album — the rank-1-only semantics at L437 would be overwritten by whatever
the star assignment happened to produce.

Same reasoning applies to `sharpness_score`/`sharpness_grade`: the original
plan made them computed "from the best passing body." build_result_entries
already computes them as `max(passing or all_bodies, key=sharpness_score)`
— note the fallback to non-passing bodies when NOTHING passed, which a
naive "best passing body" derivation loses (it would yield None/0 for every
blurry photo). Keep them stored; expose a `recompute_sharpness_from_bodies()`
method that reproduces build_result_entries' exact rule, and call it from
the grading/regrade paths.

RULE OF THUMB ADOPTED: derive nothing that any current writer sets
independently. A property is computed only if a single code path produces
it. `keep`, `stars`, `sharpness_score`, `sharpness_grade` all fail that
test and stay stored.

--- DECISION 4: PersonRecord is dict-backed and .FaceReco-compatible ---

ORIGINAL PLAN SAID: PersonRecord is "a plain, standalone VALUE OBJECT, no
back-reference," replacing BodyRecord outright.

REVISED: PersonRecord wraps the evaluated[] dict the same way AlbumImage
wraps the entry dict, and exposes:

    @property
    def wire(self) -> dict:
        """The exact evaluated[] dict this record wraps. Required because
        .FaceReco face.json embeds it verbatim as `"Body": ...` — see
        algo/facereco.py L1374/L1509 — and existing face databases on disk
        contain those embedded dicts."""

WHY THIS DIFFERS: V4. `BodyRecord.raw_body` is not redundant duplication;
it is a live pass-through into a SECOND on-disk format. A pure value object
with no back-reference cannot reproduce it byte-for-byte, so every existing
.FaceReco database would become unreadable (the dedup key at L1291 reads
`raw_body["body_bbox"]` out of the persisted copy).

Field set (union of the four shapes, all dict-backed):
  body_bbox, body_keypoints, face_bbox, narrow_face_bbox, face_kps,
  sharpness_score, lap_var, ten, is_blurry, rejection_reason, cloth_color,
  cloth_color_detail, qualified_for_sharpness, player_name, player_number.

  - `passed` is exposed as `passed` == `not is_blurry` (the wire key is
    `is_blurry`; algo/models.py::Body uses `passed`). One property, both
    names available, documented as the same fact — this is exactly the kind
    of drift the refactor exists to kill.
  - `qualified_for_sharpness` gets a docstring recording V5: written only
    by the legacy analyse_image path, absent (→ False) in every album the
    current pipeline writes. Do NOT "fix" it in this task; flag it.
  - player_name / player_number live here, not on AlbumImage — RETAINED
    from the original plan, and confirmed correct: culling_app.py L1483-84
    writes them per-body.

OPEN QUESTION RESOLVED (the original plan parked this): ONE class, not two.
Once `wire` exists, facereco's needs are a strict subset of regrade's. The
only facereco-specific field is `confidence`, which is
`face_kps["confidence"]` — a derived property, not a reason for a second
class. `orig_filename` and `body_index` are identity, not body data: they
move to a small `PersonRef(image_key, body_index, record)` used only by
facereco's collection pass.

Pixel access: RETAINED from the original plan. Caller decodes the source
photo once, then `record.crop_from(image)` does the bbox math in one place
instead of each consumer re-deriving it.

--- DECISION 5: Album.create() takes paths, it does not enumerate ---

ORIGINAL PLAN SAID: `Album.create(source_dir, *, exclude=frozenset(...))`
iterates every image file in source_dir; "directory enumeration must ONLY
happen inside Album.create()."

REVISED:

    Album.create(path, *, team_id, paths: Sequence[Path],
                 our_jersey_color=None, run_settings=None,
                 import_status="in_progress") -> Album

  plus a new shared module `algo/imagefiles.py` holding the single
  `collect_images()` + IMAGE_EXTENSIONS + _RAW_EXTENSIONS definition, and a
  caller-side helper:

    def images_to_import(source_dir, exclude: frozenset[Path]) -> list[Path]

WHY THIS DIFFERS: putting `iterdir()` inside Album drags image-format
knowledge (extension allow-list, RAW handling, sort order) into a class
whose job is one JSON file. The INVARIANT the original plan actually wanted
— "nobody enumerates behind Album's back" — is fully preserved: Album still
owns the complete AlbumImage set, and there is still exactly one
collect_images in the codebase. It's just in a module about image files
instead of a module about album.json. Album also becomes unit-testable
without a filesystem full of JPEGs.

Key assignment moves into Album.create() (this is REQUIRED by V7 — keys are
currently assigned after analysis). create() walks `paths` in order,
calls make_unique_import_key against the running `used_keys` map, and
constructs one AlbumImage per path with `file` and `key` set and no
`status` yet. This is strictly better than today: preview filenames are
knowable before any pixel is decoded.

NOTE ON ORDERING: this is the one place the narrowed scope still touches
the pipeline, because Album cannot own the AlbumImage set while the
analysis stage is also inventing entries. It is kept in scope for that
reason, but it is the LAST thing to land (Phase B2) and it changes only
WHERE the path list and keys come from — not the `process(frames, config)
-> frames` signature, which stays as-is per the scope section.

RETAINED from the original plan and CONFIRMED correct: both the fresh-album
and temp-staging-album flows go through Album.create(); there is no
append-into-an-existing-Album path; `exclude` is computed fresh by the
caller from the target's current path set with no import history.

Migration of the two existing collect_images (V8):
  - algo/stages/image_analysis.py: delete its private collect_images; the
    stage receives the path list via the EXISTING `only_paths` parameter
    (already there for deep regrade, 1_prep_review.py L1955/L1966). This
    is the original plan's approach and it is correct.
  - 1_prep_review.py L1057: delete along with the dead `process()` path.
  - autoedit.py: approved exception, untouched.

--- DECISION 6: error handling is DEFERRED (and must not be purge-based) ---

ORIGINAL PLAN SAID: a "Purge Error" stage removes every Error AlbumImage
from the album's live collection before later stages run.

REVISED: out of scope here — it depends entirely on the status lifecycle
that Decision 2 defers. No new stage, no `active_images`, no per-stage
try/except in this task.

CARRIED FORWARD so the later task doesn't repeat the mistake: PURGING IS
THE WRONG DESIGN. Dropping error entries from results[] creates an
infinite re-import loop — the next "import more images" run computes
`exclude` from the target's CURRENT path set (Decision 5), a purged file
is not in that set, so it gets re-imported, re-fails to decode, and is
re-purged, every time, forever, with no user-visible record of why.
Quarantine instead: leave the entry in results[] with its error status and
a reason field, and have consumers filter it out.

ALSO CARRIED FORWARD: the genuinely valuable half of the original section
was never the purge — it was "every stage wraps its per-image work in
try/except so one bad photo marks itself failed and the batch continues
instead of the whole run dying." That belongs with the stage rework.

--- DECISION 7: the flag is renamed, defaults to today's behaviour ---

ORIGINAL PLAN SAID: module-level `preserve_album_json_changes: bool = False`
gating the gzip backup in save().

REVISED:

    album_json_backups_enabled: bool = True

  - RENAMED because "preserve_album_json_changes" reads as "keep my
    changes" — the opposite-ish of what it does (it keeps a backup of the
    PREVIOUS contents). A future reader will misread it under pressure.
  - DEFAULT FLIPPED to True so no existing behaviour changes implicitly.
    Callers that save an album repeatedly in a batch — today that is
    1_prep_review.py — set it to False once, explicitly, where the "I am
    about to rewrite this 33 MB file and don't need a gzipped copy of each
    version" reasoning is visible at the call site.
  - Gates ONLY the backup step. `atomic_save_and_backup`'s temp-file+rename
    atomicity is NOT optional and must remain unconditional; a torn
    album.json is unrecoverable.
  - RETAINED from the original plan: it is deliberately a single global
    ambient switch, not a per-caller parameter, and the code comment must
    say so explicitly so nobody "fixes" it into a parameter.

Save-cadence note, CARRIED FORWARD for the deferred stage-rework task
(correcting the original plan's cost claim): one save per stage is the
right cadence, but it is NOT free — `json.dumps(indent=2)` with
NumpyEncoder over a ~50 MB parsed payload is on the order of seconds, not
milliseconds. Seven stages is still an acceptable price for crash
visibility; just don't document it as negligible, and do skip the gzip
backup (the genuinely expensive part) via the flag above.

FRAME/BODY HANDOFF — DEFERRED, with the answer recorded
============================================================
OUT OF SCOPE for this task. `ProcessStage.process(frames, config) ->
frames` stays exactly as it is; stages keep threading Frame lists.

Recorded so the later task starts from a decision instead of a fork — the
original plan's OPTION 2 is the right one:

  - Frame/Body remain a TRANSIENT, in-memory-only detail of the analysis
    stage. That stage alone constructs them from decoded pixels.
  - At the END of image analysis, results are written onto the Album's
    AlbumImage/PersonRecord objects (reusing algo/results.py's existing
    serialization rules, which become PersonRecord constructors — this
    part IS delivered by the current task, which is what makes the later
    one tractable).
  - Every stage AFTER analysis becomes a pure AlbumImage consumer.

Stage-by-stage boundary (from the live pipeline at 1_prep_review.py
L1983-L2101):
    ImageAnalysis      -> Frame/Body internally; writes PersonRecords out
    Grading            -> pure AlbumImage  (sets verdict + sharpness)
    JerseyCounting     -> pure AlbumImage  (needs pixels: decode on demand)
    AutoAdjust         -> pure AlbumImage  (needs pixels: decode on demand)
    Annotation         -> pure AlbumImage  (needs pixels: decode on demand)
    FaceReco           -> ALREADY album-centric (takes working_dir, reads
                          album itself; `frames` arg is vestigial)
    LLMCulling         -> ALREADY album-centric (same)

Unresolved cost question for that task: the three middle stages currently
ride on `Frame.image` / `Frame.normalized_image` to avoid re-decoding.
Measure the re-decode cost before committing to "decode on demand"; the
acceptable fallback is a stage-local `dict[str, np.ndarray]` pixel cache
passed alongside (never stored on) the Album. Do not reintroduce Frame to
solve it.

============================================================
MIGRATION STRATEGY — the gap in the original plan
============================================================
The original plan's stated goal was "no raw dict access outside
album.py," but its execution steps never touched culling_app.py (~30
sites), apply_export.py (~10) or algo/stages/llm_culling.py (~8). Goal and
plan didn't match — and that consumer migration is the actual substance of
this narrowed task. Because of Decision 1, it can be a strangler pattern
instead of a big bang: old and new access styles work simultaneously
against the same dicts.

PHASE A — build the typed layer (no callers change)
  A1. algo/imagefiles.py: single collect_images + extension sets.
  A2. algo/album.py: PersonRecord + expanded AlbumImage. Write the FULL
      field inventory as a docstring table first, listing wire key <->
      property name <-> writers, and get sign-off before implementing
      (RETAINED from the original plan's step 1 — correctly requested for
      foundational classes).
  A3. Unit tests: dict -> typed -> dict round-trip preserves unknown keys
      byte-for-byte. This is the regression test for Decision 1 and must
      exist before Phase B.

PHASE B — migrate producers
  B1. algo/results.py::build_result_entries -> construct AlbumImage/
      PersonRecord objects. Golden-file test: output JSON identical to the
      current implementation for a fixed frame set.
  B2. Album.create(paths=...) + key assignment; image_analysis.py switched
      to only_paths; delete both dead collect_images copies. Stage
      signature untouched.

PHASE C — migrate consumers (the part the original plan omitted)
  C1. algo/regrade.py — delete _body_from_entry and _full_body_from_dict.
  C2. algo/facereco.py + facereco_provider.py — BodyRecord becomes
      PersonRef + PersonRecord; `wire` keeps face.json byte-compatible.
      Test: re-run facereco against an EXISTING .FaceReco db and assert
      no cluster churn.
  C3. algo/stages/llm_culling.py — including moving `_timestamp` (V6) off
      the entry dict entirely into a local `dict[key, float]`, which is
      where it always belonged.
  C4. apply_export.py.
  C5. culling_app.py — largest surface; do it last, one endpoint group at
      a time (listing / culling / regrade / face-tagging / export).

PHASE D — close the door
  D1. Make `AlbumImage._raw` / `PersonRecord.wire` private-by-convention
      and add a grep-based guard test asserting no `["annotation_data"]`,
      `["evaluated"]`, `entry["stars"]`-style access outside algo/album.py
      (allow-list algo/facereco.py's face.json embedding).
  D2. album_json_backups_enabled + the one explicit flip in
      1_prep_review.py::main().

Each phase is independently shippable and leaves the app working. Phases A
and C carry essentially all of the value; B2 is the only one that reaches
into the pipeline and can be dropped or deferred without losing the rest.
