GUIDING PRINCIPLE
============================================================
Goal (user's own words): "clean code with proper level of abstraction
without requiring the internal data structure." Concretely: no code outside
algo/album.py should ever read/write a raw results[]/annotation_data dict
by key path (e.g. entry["annotation_data"]["evaluated"][i]["sharpness_score"]).

keep, burst_ranking, burst_caption, edited_image, status, etc.) must be
reached through typed properties/methods on AlbumImage (and a new per-person
record class), never through dict indexing by other files.

--- 1. AlbumImage — new shape ---
Convert AlbumImage from a thin dict view into a real typed object:
- Load: constructed from the corresponding JSON dict when an Album is
  loaded/parsed (a "from_dict"-style path).
- Create: brand-new AlbumImage instances are created ONLY by
  Album.create()'s directory enumeration (see Album section below) — never
  via the plain constructor being called ad hoc elsewhere.
- The JSON dict is the on-disk WIRE FORMAT ONLY. AlbumImage's fields are the
  live in-memory source of truth; Album.save() must gather every live
  AlbumImage and serialize it back into the results[] list before writing
  JSON. (This is a deliberate shift from today's "one shared cached dict"
  model — confirm you understand this ripples into Album's freshness/
  refresh/invalidate machinery: on refresh, re-parsing means re-constructing
  every AlbumImage from its dict again, not just re-exposing a dict
  reference.)

Field-by-field getters/setters (agreed: concrete, extensible, avoids
ambiguity — add new fields to the class as needed, don't build one big
"apply everything at once" method):

READ-ONLY / COMPUTED (never independently settable — derive from other
fields so two facts can never drift out of sync):
  - status: one of Unprocessed / Error / Blur / Clear / Skipped (see state
    machine below) — derived from `bodies` + an explicit lifecycle marker,
    NOT independently settable.
  - sharpness_score / sharpness_grade — derived from the best passing body
    in `bodies`.
  - keep — derived from `stars >= 3` (matches existing rule already
    documented elsewhere in culling_app.py).

INDEPENDENTLY SETTABLE (field-by-field, add more as needed later):
  - bodies: list[PersonRecord] — set as a WHOLE LIST at once (a
    (re)detection pass always produces a complete new set together; there
    is no "add one body incrementally" case in this pipeline).
  - stars, stars_manual, llm_grade, burst_ranking, burst_caption,
    auto_adjustment, edited_image (setter already exists as
    set_edited_image, keep it).
  - Existing path properties stay as read-only resolvers, unchanged:
    original_path, edited_path, preview_path, thumbnail_path, image_path,
    preview_stem, ensure_thumbnail().

NOT on AlbumImage — belongs on the per-person record instead:
  - player_name / player_number (currently set per-body by culling_app.py's
    face tagging / apply_export.py).

--- 3. AlbumImage/Album state machine (FINAL, deliberately simple) ---
status lifecycle, exactly these states, nothing more:
  Unprocessed -> Error (purged shortly after, never proceeds further)
  Unprocessed -> Blur / Clear / Skipped (set ONCE, only by the grading
    stage — this is the ONLY transition away from Unprocessed)
- Unprocessed is the initial state set the moment an AlbumImage is created
  (at enumeration time, before any pixel has even been decoded).
- Status stays Unprocessed through the entire analysis/detection stage,
  EVEN AFTER bodies have been populated — it only changes once grading
  actually runs and assigns a real verdict.
- Do NOT add a separate `processed: bool` field or any other per-stage
  tracking flag — this was explicitly considered and rejected in favor of
  keeping the single `status` field as the only lifecycle marker.
- No stage after grading (jersey-counting, auto-adjust, annotation,
  facereco, llm-culling) needs to filter on "Unprocessed" — by the time
  they run every surviving image already has a real verdict.
- EXPLICITLY OUT OF SCOPE: true crash/interruption "resume processing" (an
  interrupted run picking up exactly where it left off). A crash today (or
  after this task) is acceptable to simply "restart the whole import from
  scratch" as the failure mode. Do not build resumability logic. This needs
  its own dedicated, later design pass if ever pursued.

--- 4. Album.create() — enumeration + exclusion ---
Signature grows to include the source directory and an exclusion set:
  Album.create(source_dir, *, team_id, our_jersey_color=None,
               run_settings=None, import_status=..., exclude=<read-only
               set/frozenset of resolved Path>) -> Album
- Iterates every image file in source_dir. For each one NOT in `exclude`,
  creates a fresh AlbumImage (status=Unprocessed) and adds it to the
  Album's live collection.
- `exclude` is read-only, supplied by the caller — it represents "the
  complete current set of file paths already present in the target album."
  There is NO concept of "past imports"/history to reconstruct here (that
  tracking was already removed) — just the target's current full path set,
  computed fresh by the caller each time.
- This enumeration/creation flow already correctly covers BOTH "brand new
  permanent album" (first import) and "temp staging album for import more
  images" cases — both go through Album.create(), never through appending
  directly into an already-loaded, pre-existing Album object. (This was a
  flaw initially raised, then retracted once the temp-staging design was
  re-examined — confirm this reasoning holds before changing anything here.)
- Directory enumeration must ONLY happen inside Album.create() going
  forward. Audit already performed this session — findings:
    - algo/stages/image_analysis.py (ImageAnalysisStage and
      MediaPipeImageAnalysisStage) each have their OWN private
      collect_images(self.input_path) call — THIS is the real migration
      target. Fix: these stages already accept an `only_paths: list[Path] |
      None` parameter (added earlier for deep regrade) that bypasses
      directory scanning when given an explicit file list — reuse this.
      Album.create() enumerates + creates AlbumImages first; 1_prep_review.py
      then passes the resulting paths to these stages via `only_paths`
      instead of letting them scan the directory themselves.
    - 1_prep_review.py has a SECOND, unrelated collect_images belonging to
      a dead/legacy `process()` function (documented elsewhere as not
      called by the active main()) — DELETE this dead code, don't migrate
      it.
    - autoedit.py also scans a directory for images, but it's a
      general-purpose standalone editing tool unrelated to Album/album.json
      — treat as an approved exception, leave untouched.
  If you find any other source-directory enumeration outside Album during
  implementation, flag it rather than silently leaving it.

--- 5. Error state + Purge Error stage ---
- Add `Error` as a real status value. Set it (with a short reason/log line)
  whenever an AlbumImage's source file fails to load/decode.
- Add a new, explicit processing stage: "Purge Error" — runs immediately
  after the first stage (image loading/decoding), removing (log + drop,
  nothing fancier needed) every AlbumImage currently in Error state from
  the Album's live collection, BEFORE grading/jersey-counting/auto-adjust/
  annotation/facereco/llm-culling ever run, so later stages never waste
  time on or need to special-case images that failed to load.
- Each stage must wrap its own per-AlbumImage work in try/except: on an
  exception, catch it (never let it propagate and kill the whole script),
  mark that one AlbumImage as Error, log it, and continue with the rest of
  the batch. This applies broadly, not just to the first stage.

--- 6. Processing stage architecture rework ---
- Every stage becomes Album/AlbumImage-aware. When starting a new stage,
  ALWAYS re-retrieve the full, current set of AlbumImages fresh from the
  Album object — never carry forward a stale in-memory list threaded
  through from a previous stage's return value.
- This is a deliberate move away from today's `ProcessStage.process(frames,
  config) -> frames` signature (Frame objects threaded stage-to-stage by an
  orchestrating loop in 1_prep_review.py::main()). Decide, as part of this
  task, how far this goes:
    - Do algo.models.Frame/Body disappear entirely from the stage-to-stage
      handoff (stages operate purely on AlbumImage/PersonRecord), or
    - Do Frame/Body remain as a transient, in-memory-only detail used only
      inside the analysis stage itself (which still needs live pixels),
      with results synced onto AlbumImage/PersonRecord before any other
      stage runs?
  This was raised as an open architectural fork during design discussion
  and not fully resolved — pick a direction (the second is likely the
  smaller, lower-risk change) and be explicit about which stages still
  touch Frame/Body vs. which are pure AlbumImage consumers.
- Save cadence: call Album.save() once at the end of EACH processing stage
  (not per-image, not only once at the very end of the whole run). This is
  acceptable cost-wise (see flag below) — full-payload JSON serialize +
  fsync at "once per stage" frequency is negligible even for large albums;
  fsync's cost is a small per-call latency for durability, not proportional
  to file size.

--- 7. preserve_album_json_changes flag ---
- Add a module-level flag in algo/album.py:
    preserve_album_json_changes: bool = False
- Referenced ONLY inside Album's own persistence code path — specifically,
  gates whether Album.save() performs the existing gzip-backup-of-previous-
  contents step (via atomic_save_and_backup) or skips it entirely.
- This is DELIBERATELY a single, global, ambient switch — confirmed
  explicitly with the user. It affects EVERY Album.save() call throughout
  the entire application, including culling_app.py's interactive/manual
  saves (Apply, regrade, face tagging), not just the bulk import pipeline.
  Default False means NO album save anywhere in the app gets a backup
  unless something explicitly flips this flag on. Document this clearly in
  code comments so a future reader doesn't "fix" it into being scoped
  per-caller — it's intentional.

--- 8. Deep regrade — explicitly NOT in scope for this task ---
- Deep regrade never discovers new files — it only ever re-processes an
  existing, already-known set of paths already recorded on already-existing
  AlbumImages. It should fetch those AlbumImages directly from the
  already-loaded Album; it must never scan a directory.
- Separately (flagged during design discussion, NOT actioned, candidate for
  a LATER task): today's --regrade-only path rebuilds results[] entirely
  from scratch (build_result_entries + _merge_preserved_fields), which has
  a real bug — a source file missing from disk causes that photo's entry to
  be silently DELETED from the album (not just skipped/left unregraded).
  An in-place update (enumerate existing AlbumImage objects, overwrite only
  the detection-derived fields for photos that were actually reprocessed,
  leave everything else untouched) would fix this and is a more natural fit
  for the new AlbumImage-centric model — but this is out of scope for the
  current task per explicit user direction ("more than enough on our
  plate"). Do not attempt it as part of this task; just don't make it
  harder to do later.
